# Piのエージェント委譲

起動・状態確認・キャンセル・結果の受け取りには、導入済みの `pi-subagents` 拡張とそのスキルを使う。APIの呼び出し契約は拡張側の文書に従う。

## 起動

通常はモデル・推論強度を省略して設定値を使う。ユーザーが一時的な変更を指定した場合は、利用可能性を確認し、`model: "provider/model:effort"` で渡す。導入済み拡張では、起動時に独立したトップレベルの `thinking` フィールドを渡しても無視される。

```javascript
subagent({
  agent: "reviewer",
  context: "fresh",
  task: "指定した差分をレビューしてください。ここにリポジトリ・ref、対象範囲、制約、根拠、受け入れ条件、期待する報告形式を記載します。"
})
```

文脈の分離が役立つ場合は、必要な情報を含む自己完結した依頼を新しいコンテキストへ渡す。拡張の非同期実行と完了通知を優先し、子の実行中は親が独立して進められる作業を行う。

黙ってプロバイダーを変更したり、推論強度を下げたり、`max` へ引き上げたりしない。現在のPi本体CLIには `--fallback-models` がないため、明示的に許可された候補がある場合だけ、拡張が対応する `fallbackModels` 設定を使う。利用可能性を事前に確認し、候補の枯渇や実行基盤の障害は、保持されている実行状態とともに報告する。

CLIによる子の起動が明示的に必要な場合は、`pi --model 'provider/model:effort' -p 'instructions'` の形式を使う。必要なスキルはプロンプト内に `/skill:skill-name instructions` として指定できる。シェルの引用符を正しく扱い、失敗時の出力を保持する。バックグラウンドのCLI子プロセスはHerdrで管理する。

## 実行による受け入れ検証

実装・修正を委譲するときは、親が対象の振る舞いを確認する検証コマンドを選び、起動引数に必ず渡す。コマンド1本なら `gate`、複数本・作業ディレクトリ・タイムアウトの指定が必要なら `acceptance: { level: "verified", verify: [...] }` を使う。`gate` と `acceptance` は併用しない。子への依頼文に「テストする」と書くだけでは、実行基盤による検証は設定されない。

このrepositoryのPi品質設定を変更する場合の例:

```javascript
subagent({
  agent: "worker",
  task: "Piの品質設定を修正し、対象の検証を行ってください。",
  gate: "node modules/pi-coding-agent/tests/quality-gates.test.mjs"
})
```

検証は子の作業ディレクトリで実行される。既存のテスト・型検査などから対象を絞り、repositoryの実行制約とユーザーの許可範囲に従う。読み取り専用の調査・レビューには不要な実行ゲートを付けない。実行可能な検証がない場合は、確認方法と自動検証未実施を明示し、`verified` と報告しない。

完了判定には受け入れ台帳の `evidenceStatus` と `verifyRuns` を使う。子の成功報告だけでは通過としない。`rejected` は修正後に再検証し、`review-required` は独立レビューも完了させる。Watchdogの指摘はこの実行結果を置き換えない。
