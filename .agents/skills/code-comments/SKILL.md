# コードと説明の書き分け

コードから読める処理を重ねて説明せず、変更する人に必要な判断理由を残す。コメントやPR説明を依頼された場合、または理由が失われる具体的な懸念がある場合に使う。

| 置き場所 | 残す情報 |
| --- | --- |
| コード・識別子 | 処理と対象の意味 |
| テスト名・期待結果 | どの条件で何が起きるべきか |
| commit・PR | 解決する問題、変更理由、検証と制約 |
| コードコメント | コードだけでは分からない制約・意図・回避策 |

- 非自明な回避策には、理由と必要なら根拠となるIssueや仕様を添える。
- `Why not` は有用な観点だが、コメントをその形式だけに制限しない。API契約、単位、不変条件など必要な説明も残す。
- 自明な処理説明、古い変更履歴、不要なコメントアウトは依頼範囲で整理する。
- 説明を短くするためだけにAPIの改名や関数分割を強制しない。
- 設計判断は、そのコードを触る際に必要なら近くのコメントへ、変更全体の背景ならcommit・PRへ残す。既存ADRはrepositoryの運用に従う。
